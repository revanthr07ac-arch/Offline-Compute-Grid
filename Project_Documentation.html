Offline Compute Grid - Complete Project Documentation

Comprehensive overview of the application architecture, tools, setup commands, and technical Q&A.

1. Frontend Code & Technologies (What & Why)

  • React.js (v19): The core UI library. Used because its component-based architecture allows us to build isolated, reusable pieces of the UI (e.g., extracting a `StatusBadge` or `DeviceCard` to use across multiple pages).
  • TypeScript: A superset of JavaScript that adds static typing. Used to catch errors during development and ensure data structures (like our `DeviceType` and `Task` interfaces) are strictly enforced.
  • Vite (v8): The build tool and development server. Chosen over Webpack or Create React App because it utilizes native ES modules for near-instant hot-module replacement (HMR), drastically speeding up development time.
  • Tailwind CSS (v4): The utility-first CSS framework. Used to apply styling directly in the React components (`className="flex items-center..."`). This eliminates the need for separate CSS files, keeps styles scoped, and ensures a consistent design system.
  • Lucide React: The icon library. Chosen for its clean, scalable vector icons that perfectly match modern UI aesthetics.
  • Recharts: The data visualization library. Built specifically for React, it uses declarative components (like <AreaChart>) making it incredibly easy to feed our performance metrics directly into beautiful, responsive charts on the Dashboard.
  • React Router DOM: The routing library. Used to handle navigation between pages (Dashboard, Devices, Tasks, Profile) without reloading the browser window. This is what makes the project a Single Page Application (SPA).

2. Tools Used in the Project

  • Frontend Stack: React 19, TypeScript, Vite, Tailwind CSS, Recharts.
  • Backend Stack: Node.js, Express.js, CORS, TS-Node (added to handle API requests and replace hardcoded mock data).

4. Project Q&A (Basic to Advanced)

Basic Level

Q: What is the main purpose of this application?
A: It is a user interface dashboard for managing an "Offline Compute Grid." It allows administrators to monitor connected devices, track computational tasks (like Video Transcoding or ML Training), view real-time performance metrics, and manage system settings.
Q: What makes this a Single Page Application (SPA)?
A: Instead of the browser requesting a completely new HTML page from the server every time you click a link, we use React Router. The initial HTML is loaded once, and React dynamically swaps out the components (e.g., replacing the Dashboard with the Devices list) instantly without a page refresh.
Q: Why did we choose Tailwind CSS over traditional CSS files?
A: Traditional CSS requires bouncing back and forth between a `.css` file and a `.tsx` file, coming up with class names, and worrying about CSS specificity. Tailwind provides utility classes (like `flex`, `mt-4`, `text-blue-500`) that we apply directly in the markup. It builds faster, prevents dead CSS, and keeps the design highly consistent.

Intermediate Level

Q: How does the frontend communicate with the backend?
A: We use the native JavaScript `fetch` API. Inside our React components, we use the `useEffect` hook to trigger a network request to endpoints like `/api/devices` or `/api/tasks` immediately when the component mounts. The backend responds with JSON data, which we then store in the component's state using `useState`.
Q: What is CORS, and how are we avoiding CORS errors during development?
A: Cross-Origin Resource Sharing (CORS) is a security feature that blocks a web app running on one port (e.g., Vite on 8443) from requesting data from a server on a different port (e.g., Express on 3001). We avoid this by configuring a proxy in `vite.config.ts`. When the frontend requests `/api/tasks`, Vite intercepts it and secretly forwards it to `http://localhost:3001`, tricking the browser into thinking the request went to the same origin.
Q: How is the authentication flow handled?
A: The frontend has a state variable (`loggedIn`). When a user submits the `LoginPage` form, it sends a POST request with the email and password to the `/api/auth/login` backend endpoint. The backend validates this and returns a success response with a simulated JWT token. Upon receiving success, the frontend updates `loggedIn` to true, rendering the main dashboard routes.

Advanced Level

Q: How is the Network Topology map on the Dashboard constructed without an external mapping library?
A: It is built entirely using custom SVG (Scalable Vector Graphics) elements within React. We define a coordinate system with a central "master" node `(x: 180, y: 110)` and an array of "worker" nodes with specific X/Y coordinates. We map over the workers array to dynamically render SVG `` elements connecting the master to the workers, and apply SVG `` and `` tags for the glowing visual effects.
Q: How exactly does the in-memory backend database work in our current setup?
A: In our `backend/server.ts`, we initialize standard JavaScript arrays (like `let currentTasks = [...]`) loaded with initial mock data. When a POST request is made to create a task, we push a new object into this array. Because Node.js keeps these variables in the server's RAM, any subsequent GET requests will return the updated array. However, because it is strictly in-memory, all new data is lost if the Node server is restarted. To make it persistent, this array logic would be swapped out for SQL queries (e.g., via Prisma and SQLite).
Q: What is the purpose of the `useMemo` hook, and where is it used?
A: `useMemo` is a React hook used to cache the result of an expensive calculation between renders. In `DevicesPage.tsx`, we have a list of devices that the user can search and filter. We wrap the filtering logic in `useMemo` so that the array is only re-filtered when `searchQuery`, `activeFilter`, or the `devices` data actually changes. If the component re-renders for an unrelated reason, React simply returns the cached filtered list, saving CPU cycles.
